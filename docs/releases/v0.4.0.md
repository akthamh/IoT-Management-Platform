# v0.4.0 - Object-Oriented Multi-Tenant Core

## Objective

Extend the Multi-Tenant IoT Management Platform from dictionary- and `sqlite3.Row`-based application entities to an object-oriented core.

This release introduces `Tenant` and `Device` model classes and updates the existing tenant and device workflows to use Python objects while preserving the current CLI and SQLite architecture.

The release also prepares the platform for more tenant-aware device operations before a future web interface is introduced.

## Learning goals

- object-oriented programming concepts
- Python classes and objects
- object instances
- `__init__`
- `self`
- object attributes
- Python type hints
- optional values using `None`
- converting SQLite rows into application objects
- separating database representation from application representation
- passing objects between manager and repository modules
- maintaining multi-tenant relationships with objects
- preserving existing SQLite data and schema
- separation of responsibilities between models, managers, repositories, and database code

## Model structure

The new application models are stored in:

```text
modules/
├── models/
    ├── __init__.py
    ├── device.py
    `-- tenant.py
```

### Tenant model

A `Tenant` object contains:

```text
id
name
address
is_active
created_at
```

Example attribute access:

```python
tenant.id
tenant.name
tenant.address
tenant.is_active
tenant.created_at
```

### Device model

A `Device` object contains:

```text
id
name
category
device_type
manufacturer
model
serial_number
location
status
tenant_id
```

Example attribute access:

```python
device.id
device.name
device.status
device.tenant_id
```

The `Device` model stores the tenant relationship using `tenant_id`.

The tenant name remains part of the `Tenant` object and is not duplicated inside the `Device` model.

## Object lifecycle

### New Tenant

Before persistence, a tenant can exist as a Python object.

SQLite generates values such as:

```text
id
created_at
```

After insertion, the repository reads the saved row and returns a complete `Tenant` object.

Conceptually:

```text
User input
    ↓
Tenant data
    ↓
tenant_repository.py
    ↓
SQLite INSERT
    ↓
SQLite-generated values
    ↓
Tenant object
```

### New Device

A new device is created in Python with:

```text
id = None
```

before it is stored.

Conceptually:

```text
User input
    ↓
Device object
id = None
    ↓
device_repository.py
    ↓
SQLite INSERT
    ↓
generated device ID
    ↓
saved Device object
```

This demonstrates the difference between an object that exists only in memory and an object representing a persisted database record.

## Repository conversion

Earlier versions allowed raw SQLite rows or dictionaries to move through several parts of the application.

`v0.4.0` changes the repository boundary.

Read operations now conceptually follow:

```text
SQLite
   ↓
sqlite3.Row
   ↓
Repository
   ↓
Tenant(...) or Device(...)
   ↓
Application object
```

The manager layer therefore works with model objects rather than raw database rows.

## Device update flow

The earlier update workflow built a dictionary containing updated values.

The new workflow builds a complete `Device` object.

Conceptually:

```text
Current Device object
    ↓
User enters changes
    ↓
Updated Device object
    ↓
Review
    ↓
device_repository.update_device()
    ↓
SQLite
```

The repository uses object attributes:

```python
device.name
device.category
device.device_type
device.manufacturer
device.model
device.serial_number
device.location
device.status
device.tenant_id
device.id
```

instead of dictionary keys.

## Tenant relationship in the object model

The SQLite relationship remains:

```text
tenants.id
    ↓
devices.tenant_id
```

The Python object model represents the same relationship:

```text
Device object
    ↓
device.tenant_id
    ↓
get_tenant_by_id()
    ↓
Tenant object
    ↓
tenant.name
```

The tenant name is therefore retrieved from the related `Tenant` object instead of being duplicated as a `Device` attribute.

Tenant management:

```text
CLI
  ↓
tenant_manager.py
    ↓
tenant_repository.py
    ↓
SQLite
    ↓

```

Device management:

```text
CLI
  ↓

    ↓

    ↓

    ↓

```

For database reads:

```text

    ↓

    ↓
Model object
    ↓
Manager
    ↓
CLI
```

## Database

The OOP migration does not require a new database schema.

The platform continues to use the `tenants` and `devices` tables introduced in previous releases.

Relationship:

```text
tenants.id
    ↓
devices.tenant_id
```

The `v0.3.0` migration logic remains responsible for updating an older `devices` table when `tenant_id` is missing.

The main changes in `v0.4.0` are in the Python application layer rather than the SQLite schema.

## Why use classes here?

The platform now has stable domain entities:

```text
Tenant
Device
```

Each entity has:

- an identity
- related data
- a state
- a clear role in the application

Representing these entities as objects gives the application a consistent structure and makes future development easier.

The project does not convert every function or module into a class.

Simple responsibilities such as:

- database connection helpers
- menu functions
- input helpers
- configuration values

can remain as functions or module-level values when a class would not provide useful state or behavior.

## Validation and safety

- SQL values continue to use parameterized queries.
- Device serial numbers remain unique.
- Tenant selection remains limited to registered tenants.
- Device updates require an existing device ID.
- A `Device` with `id=None` cannot be updated as an existing database record.
- Database connections are closed after operations.
- Existing SQLite records are preserved.
- Object conversion does not change the existing database relationship.
- User confirmation remains required before saving important changes.
