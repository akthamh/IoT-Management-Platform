# v0.3.0 - Multi-Tenant Foundation

## Objective

Extend the IoT Management Platform from device-only management to a basic multi-tenant architecture.

This release introduces tenant management and connects newly registered devices to tenants using SQLite relationships.

## Database relationship

The relationship between tenants and devices is:

```text
tenants.id
    |
    v
devices.tenant_id
```

One tenant can have multiple devices.

Example:

```text
Tenant 1
|-- Device 1
`-- Device 4

Tenant 2
`-- Device 2
```

The database stores the numeric `tenant_id`, while the CLI displays the tenant name to the user.

## Tenant table

```text
tenants
----------------------------------------------------------
id           INTEGER PRIMARY KEY AUTOINCREMENT
name         TEXT NOT NULL
address      TEXT
is_active    INTEGER NOT NULL DEFAULT 1
created_at   TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

## Device table change

The existing `devices` table from `v0.2.0` was extended with:

```text
tenant_id INTEGER
```

The column references:

```text
tenants(id)
```

## Database migration

The `devices` table already contained data from `v0.2.0`.

Instead of deleting the database, the application checks whether the `tenant_id` column exists.

If the column does not exist, the database initialization process adds it using an SQLite `ALTER TABLE` operation.

This preserves the existing device data while allowing the database schema to evolve.

Existing devices were then assigned to registered tenants.

The migrated `tenant_id` column remains nullable at the database level for compatibility with existing records.

The CLI requires a tenant when registering new devices.

## SQL JOIN

Device queries now combine data from the `devices` and `tenants` tables.

Conceptually:

```sql
FROM devices
JOIN tenants
    ON devices.tenant_id = tenants.id
```

This allows the application to retrieve both:

```text
tenant_id
tenant_name
```

The ID is used internally for the database relationship, while the tenant name is displayed in the CLI.

## Application flow

Tenant management:

```text
CLI
 |
 v
tenant_manager.py
 |
 v
tenant_repository.py
 |
 v
database.py
 |
 v
SQLite
```

Device management:

```text
CLI
 |
 v
device_manager.py
 |
 v
device_repository.py
 |
 v
database.py
 |
 v
SQLite
```

Device registration now follows:

```text
Select tenant
      |
      v
Select device type
      |
      v
Enter device information
      |
      v
Review device
      |
      v
Save device with tenant_id
      |
      v
SQLite
```

## Validation and safety

- SQL values use parameterized queries.
- Tenant selection is limited to registered tenants.
- Device serial numbers remain unique.
- Existing database records are preserved during migration.
- SQLite foreign-key support is enabled.
- Tenant IDs are used internally instead of being entered as free text.
- The tenant name is displayed to the user instead of exposing database relationship details unnecessarily.
- Database connections are closed after operations.

## Manual test checklist

1. Start the program with `python main.py`.
2. List registered tenants.
3. Create a new tenant.
4. Find a tenant by ID.
5. Search for a tenant by name.
6. Search for a tenant by address.
7. Add a new device.
8. Confirm that the tenant list is displayed during device registration.
9. Select a tenant.
10. Complete device registration.
11. List devices and confirm that the tenant name is displayed.
12. Search for the device and confirm that tenant information is available.
13. Retrieve or update a device by ID.
14. Change the device's tenant.
15. Confirm that the new tenant is displayed before saving.
16. Save the update.
17. Confirm directly in SQLite that the device has the expected `tenant_id`.
18. Restart the application.
19. Confirm that tenants, devices, and their relationships remain available.
20. Confirm that existing `v0.2.0` devices were preserved.
